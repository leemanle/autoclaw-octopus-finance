# 反向核查（Reverse Brainstorming）

## 核心信条

先问「哪些流程根本不该存在」，再谈用 AI 优化它。不是优化，是删减。

- AI 做 0→80%，人做 80→100%：收集、初稿、格式归 AI；判断、核准、担责留给人。
- 选对工作流 > 选贵模型。工具再强，流程错了只会更快地做错事。
- 某流程 AI 介入一周仍没省时间 ⇒ 设计有问题 ⇒ 先删流程，再谈上 AI。
- 重大决策前，先让 AI 竭尽全力唱反调。

## Inputs to collect

先把下面几项钉死再开工，缺一项就问用户（一次问完，不要挤牙膏）：

- 这次要达成的**结果**（一句话），而不是要执行的动作清单。
- 谁承担后果：哪些环节的判断与核准不可自动化。
- 已有的同类链路：磁盘上是否已经有同类脚本、同类定时档、同类报告。先查再建，
  重复链路是本方法最容易漏掉的风险。
- 不可逆点：动真钱、下单、改规则源、删文件、对外发消息、改他人拥有者文件的正文。

## Procedure

### 第 0 步：查重与摸底（先做，不许跳）

- 找出这件事在磁盘上**已经存在的**同类物：同类脚本、同类定时档、同类报告、同类通知。
- 找出这件事的**上游与下游**：谁喂它、谁吃它的产出。
- 算清**边际成本落在谁头上**：各会话现有 active 档数、日均触发数、每日通知次数。
  新增的东西会加到谁头上、排在第几位，决定这件事值不值。
- 目的：避免「再造一条链」，也避免反转型输出重复已有对策。

### 第 1 步：并行跑两条坏想法轨道

两条轨道**独立**产出，各自至少 5 条；一边想一边过滤会把反例压没，这是本方法最常见的
失效方式。「并行」是可选手段：可以同时交给两个子代理跑，也可以在同一上下文里串行写，
两种都可以——但两条轨道必须**分别独立成列**，后写的不得回头改先写的，也不得互相参考。

**简报里的数字不是事实，是待核假设。** 任务简报或用户口述里带的现状数字
（如「有 N 条档」「N 条 run 排队」）必须直查核对；实查与简报不符时，
以实查为准，并把差异单列一条写进 Already in place 节
（例：简报说 9 条 pending、实查 1 条 ⇒ 写「简报数字与实查不符，以实查为准，来源待确认」）。
绝不在未经核对的简报数字上继续推演结论。

- 轨道 A — Cause-the-Problem：假设这个目标**注定会失败**，写 5-10 条「它会怎么变成这样」。
- 轨道 B — Worst-Possible-Solution：把这个方案**推到最坏**，写 5-10 条最坏版本长什么样。

写作要求：每条写清「触发条件 → 后果」，能落到具体物件/时点/文件，不要写
「可能会有风险」这种无处可查的空话。

### 第 2 步：逐条强反转

对每条坏想法做反转。反转的标准是**抽机制**，不是字面取反。

- 弱反转：「少加一条任务」→「反转成什么？」答不出对策 ⇒ 标 Weak-inversion，不要硬凑。
- 强反转：坏想法是「加了 3 条定时档会互相重复投递」⇒ 对策不是「少加一条」，
  而是「合并成 1 条带子步骤的档 + 派送前查当日是否已投」——抽的是「重复派送」这个机制。

### 第 3 步：分类与去重

- 反转后与原方案**没实质差别**的，归入 Already in place（已在做），但要回答
  「已有机制真的覆盖了这个风险吗」——没验证过的覆盖不算覆盖。
- 反转后指向**同一个机制**的坏想法合并成一条，计数按去重后的条目。
- 反转后仍需要**先补事实**才能判断的，标为待核，不要凭假设下结论。

### 第 4 步：输出（形态见 Output contract）

先给结论（会不会翻车、最该改哪一处），再给论据。逐只票/逐条档位给全名 + 6 位代码
（+ 交易所后缀）；行文短句，不用表格。

## 删减审查模式（问「哪些流程不该存在」）

当用户问的是流程精简而非单个决策时，走这条路径：

1. 列出当前在跑的每条流程，标出：产出是什么、谁在消费、多久跑一次。
2. 逐条问：这条产出的下游有人真用吗？没有 ⇒ 进「该删」候选。
3. 逐条问：它和另一条流程产出重复吗？重复 ⇒ 合并候选。
4. 逐条问：它一周内没省时间吗？⇒ 先删，再谈给它配 AI。
5. 只对**留下来的**流程做 AI 化：写清哪一段归 AI（0→80%）、哪一段留给人（80→100%）。
6. 输出：该删清单 / 该并清单 / 保留流程的 AI-人分工表（用短句，不用表格）。

## Output contract

输出一份 Reverse Idea Register，五个小节，顺序固定。**开头先给结论**：值不值得 +
最该改哪一处（1-2 句），再展开五小节。

1. **Inversion Register 反转登记**：逐条「坏想法 → 机制 → 反转对策」。
2. **Novel Standouts 真新对策**：现有做法里没有、需要新增的对策（排序在前）。
3. **Already in place — but is it?**：看起来已有对策的，逐条写覆盖验证结论
   （验证了什么、查了哪里、结论）；没验的写「未验证」；
   **任务简报/口述里的现状数字与实查不符的，也要在这里单列一条**。
4. **Weak-inversion flags 弱反转标记**：反不过来的、以及待补事实才能判的条目。
5. **Decision-ready next step 可执行下一步**：最多 3 条，每条带「做什么 + 谁做 + 怎么判定做完」。

删减审查模式额外输出一节：**该删 / 该并 / 保留流程的 AI-人分工**。

硬约束：

- 不给买卖建议、不写买点卖点目标价止损；纯文字短句。
- 每条结论必须可核：写清查了哪个文件/哪条记录/哪个时间点。
- 不确定就写「未验证」，不要写成「已确认」。

## Failure handling

- 坏想法只想到 1-2 条 ⇒ 说明是在防守而不是找漏洞，换一条轨道重跑，别硬凑满 5 条。
- 反转后全部与原方案雷同 ⇒ 说明问题不在方案细节而在上游目标，回去问「该不该做这件事」。
- 需要事实才能判的坏想法（如「现有档位是否已覆盖」）⇒ 先查磁盘/权威库再登记，
  跨框消息里的数值不采信，当场直查。
- 简报/口述的数字与直查冲突 ⇒ 以直查为准并单列差异，不要在未经核对的数字上继续推演。
- 用户已明确拍板 ⇒ 只做执行与风险提示，不重开质疑；把反问压缩成一句风险提示。

## Examples

**例 1｜要加流程时**

输入：给我这套系统再加 3 条每日定时任务，每条都单独通知我。

执行要点：第 0 步先直查磁盘上已有的同类档位与派送记录 → 两条轨道分别产出坏想法
（重复派送 / 通知噪声挤掉真信号 / 三条档各自取数导致同一数据源被打三遍）→ 反转得到
「合并为 1 条带子步骤的档 + 派送前查当日是否已投」→ 删减审查模式指出其中 1 条
产出无下游消费者 ⇒ 进该删清单。

**例 2｜单点决策时**

输入：这条规则闸要不要现在就加上？

执行要点：轨道 A 问「加了它怎么会失效/误伤」；轨道 B 问「把它推到最坏会误杀什么」；
反转出「先加只读影子模式，命中只记录不拦截，攒够 N 天数据再开拦截」——
这是抽机制（误伤不可逆），不是字面取反（不加）。
